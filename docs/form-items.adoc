In this chapter, you'll create an Animal content type, give it alternative names and images, and link your artists to their favorite animals.
You'll then follow those relationships in Guillotine.

_Form items_ are the building blocks of content forms.
You've already used TextLine, TextArea and Date; now you'll make a field repeatable and use selectors to reference other content.

== Create the Animal form

An animal needs a species name and may have other names, such as "Caribou" for a reindeer.
Use the display name for the species and a repeatable TextLine for its other names.

=== Task: Add alternative names

Create the Animal content type in your app:

.{app-root}/cms/content-types/animal/animal.yaml
[source,yaml]
----
include::../{app-root}/cms/content-types/animal/animal.yaml[tags=header;otherNames]
----

As with Artist, `displayNamePlaceholder` tells editors what to enter in the display name, here the species.
For the `otherNames` field:

* `type` chooses the form item, in this case TextLine.
* `name` is the property name used to store the value and expose it through GraphQL.
* `label` and `helpText` guide the editor filling out the form.
* `occurrences` allows the editor to add multiple values: `min: 0` makes the field optional, and `max: 0` means there is no upper limit.

Without `occurrences`, a field is optional and accepts a single value (`min: 0`, `max: 1`).
Setting both to `1` makes it required.
Content Studio allows editors to save drafts with missing required values, but those items cannot be marked as ready or published.

TIP: Choose field names that will last, and use `camelCase`, such as `otherNames`.
Renaming a field does not migrate its stored values, and queries using its old name will need updating.
You can change its label without changing the stored property or API field.

== Query the animal's fields

Guillotine uses `occurrences` when generating the GraphQL fields.
Both `otherNames` and `images` accept multiple values, so both become lists, even when an item has just one value.
The names are strings; the images are content references whose fields you can select.

=== Task: Fetch the lion and its image

Open Query Playground for "{cms-project-displayname}", keep *Draft* selected, and run:

[source,graphql,{subs}]
----
{
  guillotine {
    get(key: "/animals/lion") {
      displayName
      ... on {app-name-query}_Animal {
        data {
          otherNames
          images {
            displayName
            ... on media_Image {
              imageUrl(scale: "width(600)") {
                path
                queryString
              }
            }
          }
        }
      }
    }
  }
}
----

The `get` result and the items in `images` use GraphQL's `Content` interface.
As in the <<headless-api#, Headless API chapter>>, an inline fragment selects fields belonging to a more specific GraphQL type:

* `+... on {app-name-query}_Animal+` gives you access to the Animal's `data`.
* `+... on media_Image+` gives you access to the image's `imageUrl`.

These are GraphQL type names; your CMS content types are `{app-name-full}:animal` and `media:image`.
The image selector stores the image's ID, and Guillotine resolves that reference for you.

The result contains an empty `otherNames` array and one entry in `images`.
Build the image URL by joining `{api-base-url}`, `path` and `queryString`, as in the media chapter.
Change the key to `/animals/reindeer` and run the query again: `otherNames` now contains `"Caribou"`, while `images` is empty.

== Link artists to animals

A ContentSelector can reference other kinds of content, just as ImageSelector references images.
You'll use it to give each artist one optional favorite animal.

The selector narrows the available choices in two ways:

* `allowContentType` permits only the `animal` content type from this app.
* `allowPath` restricts the choices to content below `/animals`.

There is no `occurrences` setting, so the editor can select at most one animal and can leave the field empty.

| Cardi B | Lion

TIP: Reference an item when it should be edited and reused independently.
Two artists can reference the same Lion, and an edit to that animal is visible through both references.
For data that only belongs to one item, such as an artist's filmography entries, you'll use sets in the next chapter.

=== Task: Follow the reference in a query

Start with the type-filtered artist query from the Headless API chapter and select `favoriteAnimal`:

[source,graphql,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        term: {
          field: "type"
          value: { string: "{app-name-full}:artist" }
        }
      }
    ) {
      displayName
      ... on {app-name-query}_Artist {
        data {
          favoriteAnimal {
            displayName
            ... on {app-name-query}_Animal {
              data {
                otherNames
              }
            }
          }
        }
      }
    }
  }
}
----

The `favoriteAnimal` field returns a single content item.
You can read its `displayName` directly, then use an Animal fragment to select `data.otherNames`.
There is no need for a separate query to fetch the referenced animal.

With the sample selections above, the `data.guillotine.queryDsl` array contains the following items; their order may differ:

[source,json]
----
[
  {
    "displayName": "Cardi B",
    "data": {
      "favoriteAnimal": {
        "displayName": "Lion",
        "data": {
          "otherNames": []
        }
      }
    }
  },
  {
    "displayName": "Missy Elliott",
    "data": {
      "favoriteAnimal": {
        "displayName": "Reindeer",
        "data": {
          "otherNames": ["Caribou"]
        }
      }
    }
  },
  {
    "displayName": "P!nk",
    "data": {
      "favoriteAnimal": {
        "displayName": "Lion",
        "data": {
          "otherNames": []
        }
      }
    }
  }
]
----

If an artist has no selection, `favoriteAnimal` is `null`.
Compare that with the empty lists for an animal's unused `otherNames` or `images` fields.

== More form items

You now have the basics for configuring fields and linking content.
The https://developer.enonic.com/docs/cms/stable/schemas/form-items[CMS form items reference] covers the full range of form items and their settings, including https://developer.enonic.com/docs/cms/stable/schemas/form-items/imageselector[ImageSelector] and https://developer.enonic.com/docs/cms/stable/schemas/form-items/contentselector[ContentSelector].

For a file that belongs directly to one content item, https://developer.enonic.com/docs/cms/stable/schemas/form-items/attachmentuploader[AttachmentUploader] stores it as an attachment on that item, instead of creating separate media content to reference.
You can retrieve it through `attachments` and `attachmentUrl`, as you did in the <<media#, media chapter>>.
