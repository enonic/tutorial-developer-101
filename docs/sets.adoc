Some form items exist to group other form items, both visually and structurally. Collectively, these are known as sets. XP can also reuse a group of inputs across several schemas, through form fragments. This {document} explains what they are and how to use them.

NOTE: {see-prev-docs}

== Field sets

Field sets are the simplest form of sets XP offers... they group inputs visually and have no effect on the data model.

In a schema, the field set wraps the inputs it should contain.

To create a field set that contains a TextLine and a TextArea, the definition would look like this:

.A field set
[source,yaml]
----
- type: "FieldSet"
  label: "FieldSet"
  items: # <1>
    - type: "TextLine"
      name: "fieldSetTextLine"
      label: "Heading"
    - type: "TextArea"
      name: "fieldSetTextArea"
      label: "Text"
      helpText: "Write something? 🖊️"
----

<1> Use `items` to place other inputs inside the field set. A field set has no `name` of its own, since it never produces data.

== Item sets

Item sets also allow you to group input fields, but as opposed to field sets, item sets group values _both_ visually _and_ on a structural level. Item sets can be arbitrarily nested.

- The https://developer.enonic.com/docs/cms/stable/schemas/form-items/item-set[item set documentation] does a standout job of explaining exactly how they work, so check that out for an overview.

== Option sets

Option sets enable editors (working in Content Studio) to choose from a set of predefined options. This is similar to the ComboBox input, but option sets also allow options to carry extra data.

Option sets where users can select only one of a number of options are known as _single-select_ option sets. You can also use a _multi-select_ option set if the user should be able to select multiple options simultaneously. We'll look at this too in a task.

- The https://developer.enonic.com/docs/cms/stable/schemas/form-items/option-set[option set reference documentation] provides a good overview (with accompanying pictures) of how option sets work.

.A multi-select option set
image::option-set-sample.png["An input form labelled 'multi-selection'. The user has selected one out of four options. Some options contain extra data such as an image selector or other input fields.", {image-s}, align=center]

== Form fragments

_Form fragments_ facilitate a form of reuse in XP. They allow you to reuse fields across several content types, or several places within one content type.

They won't look or behave any different from if you manually typed the same fields into multiple places, but they let you keep them in sync.

Form fragments go in the `{app-root}/cms/form-fragments` directory, following the same naming pattern as the other schemas we've seen (`<fragment-name>/<fragment-name>.yaml`).

We'll see them in the upcoming task, but if you want to learn more about them, consult https://developer.enonic.com/docs/cms/stable/schemas/form-fragments[the form fragments reference documentation].

[TIP]
.When to use it
====
* *FieldSet* when the only goal is a tidier form. It changes nothing in the data.
* *ItemSet* for repeating, structured data the item owns, such as filmography entries. Each occurrence becomes an object in the data.
* *OptionSet* when editors choose between variants that carry different fields, such as a feeding behavior that may or may not list prey. If the choice carries no data, a *ComboBox* is enough.
* *Form fragment* when the same group of form items appears in several places in your app. It is pure reuse at schema level; the data looks as if you had typed the fields in each place.
====

== Tasks

So far we've theoretically presented sets. For a proper understanding of those concepts, we'll introduce some tasks. Make sure to follow along in order to strengthen your knowledge on this subject.

=== Adding an item set to {content-type-1-capitalized}

Let's add an item set to the `{content-type-1-capitalized}`. The goal will be to add a Filmography item set, featuring where and when a specific artist was featured in a movie.

To add an item set, use it as you would any other form item: place it within the `form` of a content type.

If we add it to the `{content-type-1-capitalized}` content type, it'd look something like this:

.{content-type-1-capitalized} with an added Item Set
[source,yaml,{subs}]
----
kind: "ContentType"
title: "{content-type-1-capitalized}"
description: "Information about an {content-type-1}"
superType: "base:structured"
form:

  # Other fields elided for brevity

  - type: "ItemSet"
    name: "filmography"
    label: "Filmography"
    occurrences:
      min: 0
      max: 0
    items: # <1>
      - type: "TextLine"
        name: "title"
        label: "Title"
        occurrences:
          min: 1
          max: 1
      - type: "Double"
        name: "year"
        label: "Year"
        occurrences:
          min: 1
          max: 1
        min: 0 # <2>
----

<1> Much like with field sets, use `items` to nest inputs within the item set.
<2> Type-specific settings, like the lowest value a Double accepts, go directly on the input.

Note that the remaining fields of the form have been left out in the above example.

=== Adding an option set to {content-type-2-capitalized}

In this section, we'll use option sets to add some extra data to the `{content-type-2-capitalized}` content type. The goal is:

- Add an option set for feeding behavior. Intentionally simplified, this option set should indicate whether the animal is a herbivore or a carnivore. If it is a carnivore, it should also let the user add a list of prey.
- Create a form fragment for distribution options. Because each distribution option should have the same fields, create a _form fragment_ to reuse it.
- Add an option for distribution across continents. The user should be able to select as many as they want from the 7 continents to indicate where the animal lives. Each option should have an associated `TextArea` called "notes", where the user can add more data for each option.

==== Single-select: dietary data

Open your {content-type-2} content type and add a single-select option set.  As before, we use option sets as we would any other form item.

.The `{content-type-2-capitalized}` content type with feeding behavior
[source,yaml]
----
kind: "ContentType"
title: "Animal"
description: "An animal that lives on planet Earth"
superType: "base:structured"
form:

  # other fields elided for brevity

  - type: "OptionSet"
    name: "feedingBehavior"
    label: "Feeding behavior"
    selection: # <1>
      min: 1
      max: 1
    options:
      - name: "herbivore" # <2>
        label: "Herbivore"
        helpText: "Subsists primarily on plant material."
      - name: "carnivore" # <3>
        label: "Carnivore"
        helpText: "Subsists primarily on animal tissue and meat."
        items:
          - type: "TextLine"
            name: "prey"
            label: "Prey"
            occurrences:
              min: 0
              max: 0
----

<1> This specifies that if you add feeding behavior, you must select one of the options, and you can not select more than one.
<2> The herbivore option has no associated data, so it consists solely of a label and a help text.
<3> The carnivore option allows you to optionally specify prey for the animal.

==== Multi-select: distribution

. Start by creating the form fragment. Call it `distributionData` and place it in `{app-root}/cms/form-fragments/distributionData/distributionData.yaml`. It only contains a text area:
+
.The `distributionData` form fragment
[source,yaml]
----
kind: "FormFragment"
title: "Distribution data"
form:
  - type: "TextArea"
    name: "notes"
    label: "Notes"
----

. Moving on to {content-type-2}s, add the multi-select option set.
+
.The `{content-type-2-capitalized}` content type with distribution data
[source,yaml]
----
kind: "ContentType"
title: "Animal"
description: "An animal that lives on planet Earth"
superType: "base:structured"
form:

  # other fields elided for brevity

  - type: "OptionSet"
    name: "distribution"
    label: "Distribution across continents"
    helpText: "Continents where the animal can be found in the wild"
    selection: # <1>
      min: 0
      max: 7
    options:
      - name: "africa"
        label: "Africa"
        items:
          - include: "distributionData" # <2>
      - name: "antarctica"
        label: "Antarctica"
        items:
          - include: "distributionData"
      - name: "asia"
        label: "Asia"
        items:
          - include: "distributionData"
      - name: "australia"
        label: "Australia"
        items:
          - include: "distributionData"
      - name: "europe"
        label: "Europe"
        items:
          - include: "distributionData"
      - name: "northAmerica"
        label: "North America"
        items:
          - include: "distributionData"
      - name: "southAmerica"
        label: "South America"
        items:
          - include: "distributionData"
----

<1> This specifies that you can select as many of the seven continents as you want. A `max` above `1` is what turns the option set into a multi-select.
<2> `include` pulls the fields of the form fragment into this option.

NOTE: The use of the form fragment helps us both reduce duplication and keep all options in sync. If we wanted to add more data, such as current population, we would only have to add it to the fragment to have it duplicated to all distributions.

== Querying item sets and option sets

Let's look at how option and item sets work in headless contexts.

=== Item sets

Getting item sets via GraphQL is not much different than anything else we've seen:

.Fetching an {content-type-1-capitalized} filmography
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        boolean: {
          must: [
            {
              term: {
                field: "type",
                value: {
                  string: "{app-name-full}:{content-type-1}"
                }
              }
            },
            {
              term: {
                field: "displayName",
                value: {
                  string: "Cardi B"
                }
              }
            }
          ]
        }

      }
    ) {
      displayName
      ... on {app-name-query}_{content-type-1-capitalized} {
        data {
          filmography {
            title
            year
          }
        }
      }
    }
  }
}
----

=== Option sets

When fetching option set data, you can get the list of currently selected options and each option separately.

.Querying for feeding behavior and distribution
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        boolean: {
          must: [
            {
              term: {
                field: "type",
                value: {
                  string: "{app-name-full}:{content-type-2}"
                }
              }
            },
            {
              term: {
                field: "displayName",
                value: {
                  string: "Lion"
                }
              }
            }
          ]
        }

      }
    ) {
      displayName
      ... on {app-name-query}_{content-type-2-capitalized} {
        data {
          feedingBehavior {
            _selected # <1>
            carnivore { # <2>
              prey
            }
          }
          distribution {
            _selected
            africa {
              notes
            }
          }
        }
      }
    }
  }
}

----

<1> This provides data about what the {content-type-2}'s selected feeding behavior is.
<2> This gives more data about a particular option
