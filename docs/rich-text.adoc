If you want to work with rich text, HtmlArea is the input type to go for.

This input type offers some very powerful editing capabilities and a lot of configuration options.

This whole {document} is dedicated to the https://developer.enonic.com/docs/cms/stable/schemas/form-items/htmlarea[HtmlArea input type] and the editor used to define its data.

The user-oriented documentation of the Rich text editor can be found in the https://developer.enonic.com/docs/content-studio/stable/editor/rich-text-editor[Content Studio docs].

NOTE: {see-prev-docs}

== Overview

.The HtmlArea input type with the default tools selection
image::input-type-html-area.png["A text input field with a tools ribbon just above.", {image-s}, align=center]

The HtmlArea input type gives you a multi-line input field with rich formatting options, much like what you're used to from your favorite word processor. It supports text formatting and justification, lists, links, and even lets you insert images.

You can configure the HtmlArea to be exactly what you want by dictating what formatting tools to include or exclude (the `include` and `exclude` settings, respectively), by what heading levels are allowed (`allowHeadings`), and by giving it a default value (`default`).

Additionally, the HtmlArea supports the use of _macros_, giving you the ability to insert prefabricated rich components into your markup.

== HtmlArea include and exclude

We can use the HtmlArea's settings to specify which rich text controls should be available when editing. Using a combination of `include` and `exclude`, we can customize the input's appearance.

By default, it includes a limited, but useful selection of tools at your disposal. Using `include: "*"` is the same as including the default tools.

.The HtmlArea with default configuration
[source,yaml]
----
- type: "HtmlArea"
  name: "everything"
  label: "HtmlArea"
----

If you want to exclude all controls, use `exclude: "*"`:

.The HtmlArea configured to include nothing
[source,yaml]
----
- type: "HtmlArea"
  name: "nothing"
  label: "HtmlArea with exclude: *"
  exclude: "*"
----

// TODO(xp8-verify): recapture from Content Studio 6.1
.An HtmlArea input with `exclude: "*"` and no tools.
image::input-type-html-area-no-controls.png[An HtmlArea configured to exclude all editing tools, {image-s}, align=center]

Finally, if you want to exclude most tools, but not all, you can exclude all and then add back in the ones you want:

.The HtmlArea configured to include a selection of controls
[source,yaml]
----
- type: "HtmlArea"
  name: "something"
  label: "HtmlArea with some controls"
  exclude: "*"
  include: "Format | Bold Italic Underline | JustifyBlock JustifyLeft JustifyCenter JustifyRight | HorizontalRule Blockquote"
----

.An HtmlArea with a selection of tools and `exclude: "*"`
image::input-type-html-area-some-controls.png[An HtmlArea configured to include a selection of editing tools, {image-s}, align=center]

As introduced in the beginning, for a full overview of the available text tools and HtmlArea settings, visit the https://developer.enonic.com/docs/cms/stable/schemas/form-items/htmlarea[HtmlArea reference docs].

=== Task: {content-type-2-capitalized} description

Let's add a rich-text description field to the {content-type-2} content type. The input should be optional and have at most a single occurrence. You can include any editor tools you want, but it must at least have the `Link`, `Image` and `Macro` tools, as we'll be using these later. Otherwise, configure it as you want.

== Links

In addition to good old URLs, the Rich text editor provides a more powerful way of creating links, in which you can:

- Reference other content items (possibly passing query parameters);
- If the referenced content is of type media, you can set a specific link to: open the file, directly download the file, or treat it as a regular content;
- Insert URL links of type: https, http, ftp, tel or relative;

An important feature is that when creating internal links (content or media links), XP will save references to the target items, similar to how the ContentSelector works. This is useful when looking for usage and dependencies between content items later.

NOTE: Because links are created using the item's unique id, it is perfectly safe to move items around in the tree structure, or change their path name. The links will not break.

== Macros

Macros enable you to insert custom components within your rich text field.

When the content is rendered, the macro is replaced with the actual component implementation.

Similar to content types, macros can define forms that help editors configure them.

== GraphQL API

When fetching rich text via the API, the most commonly used output is "processed HTML". This is essentially unstyled, semantic HTML, and it's up to your client to style it. Internal links, images and macros also need a little work from your client, as you will see below.

The following query returns the "Lynx" content, and the `description` field as processed HTML.

.Fetching rich text via GraphQL API
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        term: {
          field: "displayName",
          value: {
            string: "Lynx"
          }
        }
      }
    ) {
      ... on {project-name-query}_{content-type-2-capitalized} {
        data {
          description {
            processedHtml
          }
        }
      }
    }
  }
}
----

With the exception of the macro, this is all valid HTML. Look closely at the link and the image, though. The `href` is the lion's path within your project, and the `src` is the image's path on the media API, with no host in front of it. These are defaults: Guillotine does not know where your front-end lives or how it routes its pages, so it leaves the final URL to you. Each element carries a reference attribute that points to structured data about the link or image, which is what your client uses to build the URL it wants. Below, you'll learn how.

=== Links

Looking specifically at the processed HTML link output above, the most interesting part is the `data-link-ref` attribute.

This example is an internal link. To build the final URL, and to access more details about the target, extend your query with the `links` field:

.Query for link details
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        term: {
          field: "displayName",
          value: {
            string: "Lynx"
          }
        }
      }
    ) {
      ... on {project-name-query}_{content-type-2-capitalized} {
        data {
          description {
            processedHtml
            links {
              ref # <1>
              uri
              content { # <2>
                displayName
                _path
                type
              }
              pageUrl { # <3>
                baseUrl
                path
                queryString
              }
              fragment
            }
          }
        }
      }
    }
  }
}
----

<1> Matches the `data-link-ref` attribute in the processed HTML.
<2> The content item the link points to.
<3> The components of the link's page URL. `baseUrl` is the base URL configured for your project, and is `null` when you have not configured one.

By executing this query, you will get some more data. Specifically:

You now have access to the full name and type of the referenced item, and to the parts of its URL. Match the `ref` value with the `data-link-ref` attribute in the HTML, as you may have more than one link, and replace the `href` with your front-end's own route for the lion, for instance `https://www.example.com/animals/lion`. In a headless setup, your front-end decides what the URL of a content item looks like, not XP.

=== Images

Images work the same way: the `data-image-ref` attribute points to an entry in the `images` field, which holds the parts of every image URL. The default `src` is the media path, so the simplest fix is to prefix it with your media base URL - the same `{api-base-url}` you used in the <<files#, media {document}>>.

If you want to optimize how fast images load on various devices, Guillotine can also return the image in multiple different sizes (using https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/srcset[the `srcset` attribute (MDN)]). This is achieved by adding an argument to the `description` field:

.Fetching rich text with `srcset`
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        term: {
          field: "displayName",
          value: {
            string: "Lynx"
          }
        }
      }
    ) {
      ... on {project-name-query}_{content-type-2-capitalized} {
        data {
          description(processHtml: {imageWidths: [200, 500]}) {
            processedHtml
            images {
              ref # <1>
              src { # <2>
                path
                queryString
              }
              srcset { # <3>
                width
                imageUrl {
                  path
                  queryString
                }
              }
              style { # <4>
                application
                name
                aspectRatio
                filter
              }
            }
          }
        }
      }
    }
  }
}
----

<1> Matches the `data-image-ref` attribute in the processed HTML.
<2> The components of the URL for the `src` attribute.
<3> One entry per requested width, for the `srcset` attribute.
<4> The image style you applied in the editor, including which app provides it.

This time, you should find that the `<img>` element in the processed HTML includes a `srcset` with 200w and 500w candidates, and that the `images` entry holds the parts of each URL:

=== Macros

In the headless context, the client is responsible for rendering your content. In the case of macros - this gets obvious.

In the processed HTML, each macro is represented by an `<editor-macro>` element containing a unique reference key. As for links and images, this reference can be used to access detailed data fields for the macro.

.Query that fetches all macro data
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        term: {
          field: "displayName",
          value: {
            string: "Lynx"
          }
        }
      }
    ) {
      ... on {project-name-query}_{content-type-2-capitalized} {
        data {
          description {
            processedHtml
            macrosAsJson
          }
        }
      }
    }
  }
}
----


.MacrosAsJson response (extract)
[source,json]
----
...
"macrosAsJson": [
  {
    "ref": "1f8703bc-ee13-4871-89b3-937a7299abc4",

    "descriptor": "system:embed",

      "embed": {
        "body": "&lt;iframe title=\"YouTube video player\" src=\"https://www.youtube.com/embed/gr5EwZo_CHQ?si=IlkTGRuGVV7BxEOs\" height=\"315\" width=\"560\"&gt;&lt;/iframe&gt;"
