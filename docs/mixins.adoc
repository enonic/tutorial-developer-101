= Mixins
include::.variables.adoc[]
:description: Add shared editorial notes to artists and animals with a mixin, then query their values through Guillotine.

In this chapter, you'll add an Editorial mixin to Artist and Animal, enter separate notes on each, and query them through Guillotine.

A _mixin_ adds a group of fields to content types without editing each content type's schema.
Use one for fields such as editorial notes that apply across different kinds of content, or to extend built-in types such as folders and media.
Unlike a <<sets#_reuse_fields_across_options, form fragment>>, which inserts fields into a schema's form, a mixin keeps its values separately under `x`.

== Add editorial notes to artists and animals

You'll define the fields in a mixin schema, then register it in the app's CMS descriptor to choose which content types receive them.
Your app is already assigned to "{cms-project-displayname}", so the registration applies there.

[source,yaml]
----
include::../{app-root}/cms/cms.yaml[]
----

`name: "editorial"` selects the mixin from this app.
`allowContentTypes` is a regular expression matched against the full content type name; this one selects Artist and Animal.
If you chose a different app name, update the app key in the expression to match.
Leaving out `allowContentTypes` makes the mixin available on all content types in the content project where the app is assigned.

Save both files and let your running `enonic dev` watcher update the app.
For other registration options, including mixins that editors enable per content item, see the https://developer.enonic.com/docs/cms/stable/schemas/cms-descriptor#mixin-registration[CMS descriptor reference].

== Query the notes

The content type's own fields are under `data`; mixin fields are under `x`, grouped by app and mixin.
The typed fields let your client request just the values it needs.

=== Task: Fetch Lynx's notes

Open Query Playground for "{cms-project-displayname}", select *Draft*, and run:

[source,graphql,{subs}]
----
{
  guillotine {
    get(key: "/animals/lynx") {
      displayName
      x {
        {app-name-query} {
          editorial {
            notes
          }
        }
      }
    }
  }
}
----

The three levels inside `x` are the app (`+{app-name-query}+`), the mixin (`editorial`), and its field (`notes`).
Dots in the app key become underscores in the GraphQL field name.
Unlike the content type's `data`, `x` is available on the shared `Content` interface, so this query needs no Animal inline fragment.

The response contains:

[source,json,{subs}]
----
{
  "data": {
    "guillotine": {
      "get": {
        "displayName": "Lynx",
        "x": {
          "{app-name-query}": {
            "editorial": {
              "notes": [
                "Review the habitat description.",
                "Add a source for the diet information."
              ]
            }
          }
        }
      }
    }
  }
}
----

Change `key` to `/artists/cardi-b` and run the same query to retrieve Cardi B's note.
The typed `notes` field returns a list, even when the content item has only one note.

=== Task: Inspect the JSON representation

To inspect all mixin values without selecting their individual fields, query `xAsJson`:

[source,graphql]
----
{
  guillotine {
    get(key: "/animals/lynx") {
      xAsJson
    }
  }
}
----

The `xAsJson` value contains:

[source,json,{subs}]
----
{
  "com-example-{app-name}": {
    "editorial": {
      "notes": [
        "Review the habitat description.",
        "Add a source for the diet information."
      ]
    }
  }
}
----

Notice the app key: the JSON representation uses hyphens (`com-example-{app-name}`), while the typed GraphQL field uses underscores (`+{app-name-query}+`).
The values are the same, but JSON does not apply the GraphQL field types: a single note appears as a string in `xAsJson`, while the typed field remains a list.
Use the typed fields when your client needs a predictable shape and only selected values.
The https://developer.enonic.com/docs/cms/stable/content/mixins[CMS mixins reference] covers the underlying storage in more detail.

== Mixins from other apps

Apps can provide mixins for content types they do not define.
For example, the https://market.enonic.com/vendors/enonic/seo-metafields[SEO Meta Fields app] provides fields for search and social sharing metadata across content types and exposes them through Guillotine.
The same registration mechanism lets an app add shared fields without changing your Artist or Animal schemas.

== Choosing the right tool

You've now used the main content modeling tools in this tutorial.
Use this recap when deciding how to represent new content:

[%header,cols="1,2,2"]
|===
|Tool |Use it for |Result

|Content type
|A kind of content editors create and manage independently
|A content item with its own path, lifecycle and form data

|Reference (ContentSelector, ImageSelector)
|Connecting content items that exist independently
|A stored target ID that Guillotine can resolve to content

|Media
|Images and other uploaded files
|A media content item with the uploaded file as an attachment

|FieldSet
|Grouping related fields in the editor
|Fields stored at the same level, with no extra data wrapper

|ItemSet
|Grouping fields into an object, optionally repeated
|An object or a list of objects under the item's data

|OptionSet
|Selecting options with their own fields
|A structure recording the selected options and their values

|Form fragment
|Reusing form items within schemas
|Fields inserted in place, with no wrapper named after the fragment

|HtmlArea
|Formatted prose with links, images and macros
|Stored HTML; Guillotine exposes raw and processed HTML plus structured reference data

|Mixin
|Adding shared fields across content types or to types you do not own
|Values under `x`, grouped by app and mixin
|===
