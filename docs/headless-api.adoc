Enonic is a highly flexible CMS, capable of delivering content in many ways. In this {document} we will focus on delivery via the out-of-the-box GraphQL API.

Now that we've created some content, let's see how we can access and use it via an API - headless style.

NOTE: {see-prev-docs}

== Guillotine

Introducing _Guillotine_, the app that's responsible for automatically generating a GraphQL API for your content.

Guillotine should be pre-installed based on the `Essentials` template you used when setting up your sandbox. It is available on https://market.enonic.com/vendors/enonic/guillotine[Enonic Market], and may also be installed manually.

NOTE: This tutorial is written for Guillotine 9, which requires XP 8.1 or newer. Check the version in `XP menu` -> `Applications` if your queries do not behave as described.

Guillotine exposes a single API endpoint for all your projects. On your sandbox, it is `{graphql-url}`. We'll use it directly in the <<deployment#, deployment {document}>>. For now, Content Studio offers a much more comfortable way to explore it.

== Query Playground

Back in Content Studio, you should now have access to a new item called `Query Playground` in the menu bar on the left. Open it, and you should see this:

Query Playground is an interactive GraphQL API explorer. You enter your query in the editor in the middle and when you execute it, you'll get the results of the query in the panel on the right.

GraphQL is a graph "query language". It allows you to create highly specific queries for exactly the content that you need (visit the https://graphql.org/learn/[official GraphQL docs to learn more]).

As an example of how to retrieve some minimal info about your previously created artists, run the following query:

[source,GraphQL]
----
{
  guillotine {
    getChildren(key:"/artists") {
      displayName
      _path
      _id
    }
  }
}
----

After running, you should get something like this in the response panel:

=== Getting around

Before trying to come up with complex queries, let's familiarize ourselves with Query Playground. It consists of a few panels:

Docs:: Opens on the left, and lets you browse every type and field in the API. We'll use it in a moment.
Query:: The editor in the middle, where you write your query. Press the play button, or kbd:[ctrl+enter], to run it.
Response:: The panel on the right, showing the result of the query, or any errors.
Variables:: Expands below the query editor, and lets you supply query variables as a JSON object.
Draft / Master:: The buttons above the response panel select which branch to query. Draft is your work in progress, Master is what has been published.

Queries run in the project currently selected in Content Studio's top bar, so you never have to tell Query Playground which project to use.

=== Schemas

Now, locate and open the Docs panel. Here you have detailed info about all https://graphql.org/learn/schema/[schemas] available in your project.

In the search field of the Docs panel, search for `artist` and locate the `{project-name-query}_{content-type-1-capitalized}` schema:

.The Artist schema
image::query-playground-artist-schema.png[Query playground docs section showing the details of the Artist schema, 777w]

Note that it says that the `{content-type-1-capitalized}` schema _implements_ the `Content` schema. This basically means that the `{content-type-1-capitalized}` schema will have the structure defined by the `Content` schema, together with possibly some additional structure... in this case, that additional structure is a `data` field, defined by the `{project-name-query}_{content-type-1-capitalized}_Data` schema:

.The Artist data schema
image::query-playground-artist-data-schema.png[Query playground docs section showing the details of the Artist data schema, 777w]

NOTE: Note that this matches the structure defined by the Artist content type, which is a natural thing to expect. The name of the schema is derived from your app name and the content type name, with dots replaced by underscores.

=== Querying with inline fragments

We've used the Docs panel to inspect the structure of the `{content-type-1-capitalized}` schema. Now, based on a broader understanding of this schema, we'll query to get proper data from artists.

Close the Docs panel, head back to the editor and remove `displayName`, `_path` and `_id` from the query we introduced earlier.

Now, with your cursor on the inner curly braces of the query, press kbd:[ctrl+space] to get a list of suggestions about what fields you can request in your query:

image::query-playground-artist-query-inspection.gif[Query playground query section showing suggested fields for content schema, 654w]

As can be seen, we do not have the artist `name` and `about` fields available, and the reason for that is because the `getChildren` field can return any content that implements the `Content` schema, but it can't directly infer what schema that is, which in this case is the `{project-name-query}_{content-type-1-capitalized}` schema:

.getChildren can't directly infer what schema is implementing the Content schema
image::query-playground-getChildren-infer.png[Query playground getChildren can't directly infer what schema is implementing Content schema, 331w]

So to proceed, we use https://graphql.org/learn/queries/#inline-fragments[inline fragments]:

[source,GraphQL,{subs}]
----
{
  guillotine {
    getChildren(key: "/{content-type-1}s") {
      ... on {project-name-query}_{content-type-1-capitalized} {
        _id
        data {
          name
          about
        }
      }
    }
  }
}
----

With this, we basically built a query that understands that under the `"/{content-type-1}s"` path we have content of type `{content-type-1-capitalized}`, and based on this we can request general content data, such as `_id`, but also specific content data, such as the artist's name and about:

.Getting specific data of artists
image::query-playground-artists-data.png[Query playground query returning artists content together with its name and about data, 945w]

=== Query with dataAsJson

If you don't need or care about types when creating your queries, you can ignore the previously presented inline fragment approach and use the field `dataAsJson`:

[source,GraphQL,{subs}]
----
{
  guillotine {
    getChildren(key: "/{content-type-1}s") {
      _id
      dataAsJson
    }
  }
}
----

.Getting all data using dataAsJson
image::query-playground-artists-dataAsJson.png[Query playground query returning artists content together with its name and about data - using dataAsJson field, 945w]

== Advanced queries

We'll now introduce and show examples of usage of different fields underneath the `guillotine` field, that allow us to search the system for specific data.

=== QueryDsl

There is a `queryDsl` field underneath `guillotine` which allows you to search the system for what you want (the "Dsl" stands for "Domain Specific Language").

The syntax is based on two types of operators: `Expressions` and `Compound`.

`Expression`:: Used to check particular fields for various native and analysed values.
`Compound`:: Used to logically combine various expressions and compounds to fetch nodes based on complex conditions.

In order to exemplify this field's usage, we'll query the data set we've created so far in this guide:

.A Guillotine query using some of the arguments mentioned.
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        term: {
          field: "type",
          value: {
            string: "{project-name-full}:{content-type-1}"
          }
        }
      },
      first: 1,
      sort: [{
        field: "displayName",
        direction: DESC
      }]
    ) {
      _id
      displayName
    }
  }
}
----

Note that this query is getting the last artist when sorted alphabetically by name, regardless of where the content is located in the tree structure.

// TODO(xp8-verify): confirm the _allText field name and the ngram results against XP 8.1
The following GraphQL query uses the https://developer.enonic.com/docs/code/stable/storage/dsl#ngram[n-gram functionality] to find all the {content-type-1}s that have a term (part of a text) that starts with `rap` somewhere in their data:

.A Guillotine query using _nGram_ search functionality
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        boolean: {
          must: [
            {
              term: {
                field: "type",
                value: {
                  string: "{project-name-full}:{content-type-1}"
                }
              }
            },
            {
              ngram: {
                fields: ["_allText"],
                query: "rap"
              }
            }
          ]
        }
      },
      sort: [{
        field: "displayName",
        direction: DESC
      }]
    ) {
      _id
      displayName
    }
  }
}
----

Naturally, you can also use the standard boolean operators to combine or negate clauses. If you wanted to find all {content-type-1}s that mention both rapping and singing, you could try a query like this:

.Querying for {content-type-1}s who both rap and sing
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        boolean: {
          must: [
            {
              term: {
                field: "type",
                value: {
                  string: "{project-name-full}:{content-type-1}"
                }
              }
            },
            {
              ngram: {
                fields: ["data.about"]
                query: "rap sing"
                operator: AND
              }
            }
          ]
        }
      },
      sort: [{
        field: "displayName",
        direction: DESC
      }]
    ) {
      _id
      displayName
    }
  }
}
----

NOTE: If you've previously used the Elasticsearch API to query data, you'll be quite familiar with how `queryDsl` works!

TIP: To learn more about queryDSL capabilities, visit the https://developer.enonic.com/docs/code/stable/storage/dsl[DSL reference]

=== QueryDslConnection

Just like there is a `queryDsl` field underneath `guillotine`, the API also provides other fields such as `queryDslConnection`.

We'll not go into much detail, but basically, the fields with _connection_ in their name have extra parameters for aggregating and paginating data.

To finish this {document}, we'll add a new _birthday_ field to the artist content type, update all artists to have data in this field, and then use the `queryDslConnection` field to get aggregated data. Let's get to work!

. Start by updating the Artist content type to the following structure:
+
[source,yaml,{subs}]
----
kind: "ContentType"
title: "{content-type-1-capitalized}"
description: "Information about an {content-type-1}"
superType: "base:structured"
form:
  - type: "TextLine"
    name: "name"
    label: "Name"
    helpText: "The {content-type-1}'s name (if different from their professional moniker)."
  - type: "TextArea"
    name: "about"
    label: "About the {content-type-1}"
  - type: "Date"
    name: "birthday"
    label: "Birthday"
----
+
TIP: If you are not running the project in dev mode (`enonic dev`, introduced in an earlier {document}), make sure to run `enonic project deploy` in the terminal in the project's root directory

. Update each of the previously created artists with the following dates:
+
- P!nk: 1979-09-08
- Missy Elliott: 1971-07-01
- Cardi B: 1992-10-11

. Go back to Query Playground and reopen it, so that it reloads the schema. The Artist data schema now contains the birthday field, in sync with the Artist content type structure.

. Run the following query in the playground:
+
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDslConnection(
      query: {
        boolean: {
          must: [
            {
              term: {
                field: "type"
                value: {
                  string: "{project-name-full}:{content-type-1}"
                }
              }
            },
            {
              exists: {
                field: "data.birthday"
              }
            }
          ]
        }
      }
      aggregations: [{
        name: "generationsAggregation"
        dateRange: {
          field: "data.birthday"
          ranges: [
            {
              key: "The Greatest Generation"
              from: "1901"
              to: "1927"
            }
            {
              key: "The Silent Generation"
              from: "1928"
              to: "1945"
            }
            {
              key: "The Baby Boomer Generation"
              from: "1946"
              to: "1964"
            }
            {
              key: "Generation X"
              from: "1965"
              to: "1980"
            }
            {
              key: "Millennials"
              from: "1981"
              to: "1996"
            }
            {
              key: "Generation Z"
              from: "1997"
              to: "2012"
            }
            {
              key: "Gen Alpha"
              from: "2013"
              to: "2025"
            }
          ]
        }
      }]
    )
    {
      aggregationsAsJson
    }
  }
}
----
