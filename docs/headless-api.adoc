In this chapter, you'll query your artists through Guillotine, Enonic's GraphQL API, and see how changes to your content model appear in the API.

== Guillotine

Guillotine generates a GraphQL API from your content types, letting you query both common content fields and the fields you define in YAML.

It was installed with the `Essentials` sandbox template.
You'll explore it through Content Studio's Query Playground.

NOTE: This tutorial is written for Guillotine 9, which requires XP 8.1 or newer. Check the version in `XP menu` -> `Applications` if your queries do not behave as described.

== Query Playground

Back in Content Studio, click the GraphQL icon in the menu bar on the left to open Query Playground:

image::api-playground.png["Query Playground in Content Studio, with the query editor on the left, response panel on the right, and Draft selected", width=1440]

Query Playground is an interactive GraphQL API explorer. You enter your query in the editor in the middle and when you execute it, you'll get the results of the query in the panel on the right.

GraphQL lets you request exactly the fields you need from an API.
The https://graphql.org/learn/[official GraphQL documentation] explains the query language in more detail.

Select your "{cms-project-displayname}" project and the *Draft* branch in Query Playground.
Keep Draft selected throughout this chapter so your queries include the changes you make in Content Studio.

=== Task: Query your artists

Use `queryDsl` to find content by its type.

. *Find artists by content type* - Run this query to retrieve up to ten artists, sorted by display name:
+
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        term: {
          field: "type"
          value: { string: "{app-name-full}:artist" }
        }
      }
      first: 10
      sort: [{ field: "displayName", direction: ASC }]
    ) {
      displayName
      _path
      _id
    }
  }
}
----
+
You should get Cardi B, Missy Elliott and P!nk in the response panel, in that order.
The response has this structure, with the results in the `data.guillotine.queryDsl` array.
Your content IDs will differ from these example values, and the paths depend on the names you gave your items:
+
.Example response
[source,json]
----
{
  "data": {
    "guillotine": {
      "queryDsl": [
        {
          "displayName": "Cardi B",
          "_path": "/artists/cardi-b",
          "_id": "a0d019c7-b37a-4eaa-a2d0-96a005dc33ff"
        },
        {
          "displayName": "Missy Elliott",
          "_path": "/artists/missy-elliott",
          "_id": "3caace62-9527-4174-8024-939a91945a07"
        },
        {
          "displayName": "P!nk",
          "_path": "/artists/pnk",
          "_id": "e079cf41-527a-474f-8a9f-89a1826f14d8"
        }
      ]
    }
  }
}
----

. *Try sorting and limiting results* - Change `first` to `1` and `direction` to `DESC`, then run the query again.
You should get only P!nk, the last artist alphabetically.

. *Return to the query defaults* - Remove the `first` and `sort` arguments before continuing.
Without `first`, `queryDsl` returns up to ten results; without `sort`, it uses relevance order.
The remaining examples use these defaults, so results may appear in a different order from the sample responses.

The `term` matches the full content type name, including your app's namespace.
The Artists folder keeps your content organized, but this query finds artists anywhere in the selected content project.
`first` limits the number of results, and `sort` puts them in alphabetical order.

=== Getting around

Before trying to come up with complex queries, let's familiarize ourselves with Query Playground. It consists of a few panels:

Docs:: Opens on the left, and lets you browse every type and field in the API. We'll use it in a moment.
Query:: The editor in the middle, where you write your query. Press the play button, or kbd:[ctrl+enter], to run it.
Response:: The panel on the right, showing the result of the query, or any errors.
Variables:: Expands below the query editor, and lets you supply query variables as a JSON object.
Draft / Master:: The buttons above the response panel select which branch to query. Draft is your work in progress, Master is what has been published.

Queries run in the project currently selected in Content Studio's top bar, so you never have to tell Query Playground which project to use.

=== Task: Explore the GraphQL types

The YAML content type schema you wrote defines the Artist form and its data in the CMS.
Guillotine uses that definition to generate GraphQL types for querying your artists.
These types are part of the _GraphQL schema_: the API's description of the types, fields and operations available to query.
The https://graphql.org/learn/schema/[GraphQL documentation] explains schemas and types in more detail.

. *Find the Artist GraphQL type* - Open the Docs panel to explore those types.
Search for `artist` and locate the `+{app-name-query}_Artist+` object type:
+
.The Artist GraphQL type
image::api-doc.png["Query Playground Docs panel showing the Artist GraphQL object type, its Content interface, and common fields", width=477]

. *Find the form fields* - Follow the Artist object type's `data` field to `+{app-name-query}_Artist_Data+` in the Docs panel and find `legalName` and `about`.
These are the fields you defined in your YAML form.

Notice that the Artist object type _implements_ the `Content` interface.
An interface defines fields shared by the object types that implement it.
Here, `Content` defines common content fields such as `displayName`, `+_path+` and `+_id+`, so you can request them for any content item.

NOTE: Your CMS content type is named `{app-name-full}:artist`, and its generated GraphQL object type is `+{app-name-query}_Artist+`.
The app namespace carries over to the API, keeping the types from different apps apart.

=== Task: Select the Artist fields

You've inspected the Artist GraphQL type in the Docs panel.
Now you'll query the fields from your content type's form.

. *Prepare the result selection* - Close the Docs panel, head back to the editor and remove `displayName`, `+_path+` and `+_id+` from the query we introduced earlier.

. *Explore the available fields* - Put your cursor inside the result selection braces immediately after `queryDsl(...)`, and press kbd:[ctrl+space] to see which fields you can request.
Look for the common fields `displayName`, `+_path+` and `+_id+` in the suggestions.

. *Query the Artist fields* - Run this query with an inline fragment to access the Artist's `data` fields:
+
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        term: {
          field: "type"
          value: { string: "{app-name-full}:artist" }
        }
      }
    ) {
      ... on {app-name-query}_Artist {
        _id
        data {
          legalName
          about
        }
      }
    }
  }
}
----

The autocomplete suggestions omit `legalName` and `about` because those fields belong to the Artist's `data` type.
`queryDsl` returns the general `Content` interface, even when its filter selects only artists.
The filter controls which items match; it does not change the query field's declared GraphQL return type.
To select the Artist type's own fields, use an https://graphql.org/learn/queries/#inline-fragments[inline fragment].
The syntax `+... on {app-name-query}_Artist { ... }+` means "for results whose GraphQL type is Artist, select the fields inside this block."

The filter selects artists, and the inline fragment lets you request their `legalName` and `about` fields under `data`, along with the general content field `+_id+`.
Below is one example item from the `data.guillotine.queryDsl` array.
The field values depend on what you entered in Content Studio:

.One artist result
[source,json]
----
{
  "_id": "a0d019c7-b37a-4eaa-a2d0-96a005dc33ff",
  "data": {
    "legalName": "Belcalis Marlenis Almánzar",
    "about": "Belcalis Marlenis Almánzar (born October 11, 1992), known professionally as Cardi B, is an American rapper and songwriter."
  }
}
----

=== Task: Retrieve one artist

When you know an item's path or ID, use `get` to retrieve it directly.

. *Fetch an artist by path* - Copy Cardi B's `+_path+` from the first response and use it as the `key` below:
+
[source,GraphQL,{subs}]
----
{
  guillotine {
    get(key: "/artists/cardi-b") {
      displayName
      ... on {app-name-query}_Artist {
        data {
          legalName
          about
        }
      }
    }
  }
}
----

. *Fetch the same artist by ID* - Replace the path with Cardi B's `+_id+` from your first response and run the query again.
Both keys retrieve the same item.

An ID stays the same when an item is renamed or moved; its path changes.
If the key does not match an item in the selected project and branch, `get` returns `null`.

The result is one object under `data.guillotine.get`, rather than an array of results.
Like `queryDsl`, `get` returns the `Content` interface, so you use an inline fragment to select the Artist fields.

=== Task: Inspect the form data

For a quick look at all stored form data, use `dataAsJson`.

. *Fetch the stored form data* - Update the single-artist query to:
+
[source,GraphQL]
----
{
  guillotine {
    get(key: "/artists/cardi-b") {
      displayName
      dataAsJson
    }
  }
}
----

This returns all stored form fields without selecting them individually.
At this point, your Artist form has only `legalName` and `about`.
The object under `data.guillotine.get` looks like this, with the values you entered in Content Studio:

.Cardi B's form data
[source,json]
----
{
  "displayName": "Cardi B",
  "dataAsJson": {
    "legalName": "Belcalis Marlenis Almánzar",
    "about": "Belcalis Marlenis Almánzar (born October 11, 1992), known professionally as Cardi B, is an American rapper and songwriter."
  }
}
----

Use `dataAsJson` to inspect stored values.
Use typed fields when you want to select specific fields or follow references, which you'll try in a later chapter.

== Search your content

The `queryDsl` field also supports text searches.
The "Dsl" stands for "Domain Specific Language": the structured query you pass to it describes which content to find.

=== Task: Find artists by their description

. *Search the artist descriptions* - Keep the Artist type filter and add a text search on `data.about`:
+
[source,GraphQL,{subs}]
----
{
  guillotine {
    queryDsl(
      query: {
        boolean: {
          must: [
            {
              term: {
                field: "type"
                value: { string: "{app-name-full}:artist" }
              }
            }
            {
              ngram: {
                fields: ["data.about"]
                query: "rap"
              }
            }
          ]
        }
      }
    ) {
      displayName
      ... on {app-name-query}_Artist {
        data {
          about
        }
      }
    }
  }
}
----

The `boolean.must` list requires both conditions to match: the item must be an Artist, and its `about` text must match `rap`.
The `ngram` expression finds partial words, so it can match "rapper".
With the example descriptions, you should get Cardi B and Missy Elliott.
The query returns each description so you can see why it matched.

If your descriptions use different words, change `rap` to part of a word you entered, or edit a description in Content Studio, save it and run the query again.
The https://developer.enonic.com/docs/code/stable/storage/querying[Query DSL reference] covers more search expressions and combinations.

== Other clients

From outside Content Studio, send these same queries to `{graphql-url}`.
This endpoint is shared by all content projects.
An external client must specify the content project and branch, and authenticate to read drafts; Query Playground supplies that context for you.

For example, the single-artist query with explicit project and branch arguments looks like this:

[source,GraphQL,{subs}]
----
{
  guillotine(project: "{cms-project-id}", branch: "draft") {
    get(key: "/artists/cardi-b") {
      displayName
    }
  }
}
----

The `project` argument is the content project's identifier, `{cms-project-id}`, rather than its display name, "{cms-project-displayname}".
Setting `branch: "draft"` selects unpublished work; it does not authenticate the request.
Use `branch: "master"` to read published content.

Guillotine is a _Universal API_, served at `/api/<app>:<name>`.
Its API name, `com.enonic.app.guillotine:graphql`, follows the API base URL, `{api-base-url}` on your sandbox.
The media APIs you'll use in the <<media#, next chapter>> follow the same pattern.

For browser requests from another origin, the server must allow that origin through CORS.
The Guillotine documentation covers https://developer.enonic.com/docs/guillotine/stable/usage#curl[cURL requests], https://developer.enonic.com/docs/guillotine/stable/usage#third-party-clients[third-party GraphQL clients] and https://developer.enonic.com/docs/guillotine/stable/configuration#config_file[CORS configuration for browsers].
For a complete JavaScript request, see the https://developer.enonic.com/docs/guillotine/stable/usage#javascript[Guillotine usage examples].
