In this chapter, you'll create a content project in Content Studio, define your first content type, and create and publish some content.

== Content Studio

Content Studio is Enonic's editorial interface, where editors create and curate content without technical skills. It is already installed in your sandbox: open it from `XP menu` -> `Content Studio`.

Content Studio has three parts: a project bar across the top, a menu bar on the left, and a main panel that fills the rest. The menu bar holds the content navigator, items contributed by installed apps, and *Settings* at the very bottom. For more than this chapter covers, see the https://developer.enonic.com/docs/content-studio[Content Studio documentation].

=== Task: your first project

When you open Content Studio for the first time, it offers to create a project:

.No projects found dialog
image::cs-project-create.png["Content Studio dialog offering to start the project wizard", width=660]

Content in Enonic is stored in _content projects_, or simply _projects_.
Each project has its own permissions, languages and other settings, and its own selection of apps.

Click btn:[Start Project wizard] and follow the steps to create your first project:

. Choose a default language, for instance `English`.
. Give the project the display name "{cms-project-displayname}". The identifier is derived from it, and becomes `{cms-project-id}`.
+
NOTE: The project identifier is important, and cannot be changed later. Later chapters refer to the project as `{cms-project-id}`, so stick with that name if you want to copy their examples verbatim.
+
. Choose the `Public` access mode. This lets anyone read published content, which is what you want for a public website, for instance.
. No need to change the roles. You are the super user, so you already have access.
. In the "Applications" step, select the `Developer 101` app you deployed earlier.

.Project summary showing the values you have set in the wizard
image::cs-project-summary.png["Content Studio project creation summary", width=910]

TIP: Only apps that contain a CMS descriptor, `cms/cms.yaml`, can be assigned to a project. The vanilla starter includes one out of the box.


== What are content types?

Every content item has a content type, which defines the data fields the item can and must have. Content Studio validates the item against its content type as editors fill in the form.

Content types are defined in apps, while content projects hold the content. Assigning an app to a project is what connects the two: editors can then create the app's content types in that project. This also means you may re-use the same apps and schemas across multiple projects.

XP also ships with built-in content types, such as Folder, that are available in every project.

=== Task: your first content type

You'll create a custom content type Artist for artists, with two fields. Later, when editors create an Artist content item, Content Studio will show this form:

.The Artist form in Content Studio
image::cs-artist-form.png["The Artist form, with a display name field showing the Stage name placeholder, and the Legal name and About the artist fields", width=546]


Content types live in `{app-root}/cms/content-types/`, which the starter created. XP expects each content type in a directory of its own, with a dedicated yaml descriptor file:

. Add the following file to your app and save it:
+
.{app-root}/cms/content-types/artist/artist.yaml
[source,yaml]
----
include::../{app-root}/cms/content-types/artist/artist.yaml[tags=header;basics]
----
+
* `kind`: Every schema file starts by declaring what kind of schema it is.
* `title`: The name editors see when they create content.
* `description`: Optional, but it helps your editors.
* `displayNamePlaceholder`: The hint shown in the built-in display name field, here telling editors it holds the artist's stage name.
* `form`: The fields editors fill in.
* `type` and `label`: The kind of input editors see, and its label.

. `enonic dev` should still be running from the previous chapter. It redeploys your app automatically. If you stopped it, run `enonic dev` in the app folder again.

NOTE: XP validates the schema when it deploys, and reports mistakes such as `helptext` instead of `helpText` in the sandbox log.


=== Display name field

Every content type has a built-in display name, so don't add a `title` or `name` field that stores the same thing. Here the display name is the artist's stage name and `legalName` is the name on their official documents, which is why both earn their place. Add a field only when it carries different information from the item's display name. Also notice how the `displayNamePlaceholder` sets a different placeholder text for the display name field.

TIP: Content types have more optional settings, described in https://developer.enonic.com/docs/cms/stable/content/content-types[the reference documentation].

=== Names and namespaces

XP identifies the content type you just created as `{app-name-full}:artist` - the app name, a colon, and the file name. The app name acts as a _namespace_: everything an app ships, from content types to mixins and APIs, is prefixed with it. This isolates the schemas and functionality of one app from every other app on the same instance, so two apps never conflict, even if both define a content type called `artist`.

XP's built-in content types have namespaces of their own, such as `base:folder` for the folder you created and `media:image` for images, which are reserved for XP.
Your Artist content type already refers to one: `superType: "base:structured"`.
In the next chapter, you'll use these full names, namespace included, to filter content by type.

NOTE: Read more about https://developer.enonic.com/docs/cms/stable/schemas/namespaces[namespaces] in the CMS reference docs.

== Publishing

Every content project has two branches under the hood.
You create and edit content in the _draft_ branch, and publishing copies it to the _master_ branch, which holds the published content.

When you edit published content, only the draft branch changes - until you publish again.

During the editing process, Content Studio has different workflow statuses like _Invalid_, _Work in progress_, and _Ready for publishing_.

=== Task: Publish all items

. In our case, the content items should all be _Work in progress_. To publish all items at once, select the "Artists" folder, right-click, and choose btn:[Publish]. The publishing wizard will appear.
+
.The publishing wizard
image::cs-publish.png["The publishing wizard in Content Studio", width=910]
. Click the btn:[include child items] checkbox, and then btn:[Apply]. The whole tree of content under the "Artists" folder will now be included in the publication.
+
.The publishing wizard with child items included
image::cs-include-children.png["Once the include child items checkbox is selected and Apply is clicked - all the unpublished child items are also listed", width=910]
. The publish button is still disabled, because the items are not yet marked as ready for publishing. Click btn:[Mark as ready], and the publish button will become enabled.
. Click btn:[Publish Now (4)] to publish all items in a single batch.

After completing the publication, publishing state should have changed from Offline to Online.

TIP: You can also publish a piece of content by using the keyboard shortcut: Windows: kbd:[Ctrl+Alt+P] | Mac: kbd:[control+option+P].
