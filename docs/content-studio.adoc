== Content Studio

Content Studio is Enonic's editorial interface, where editors create and curate content without technical skills. It is already installed in your sandbox: open it from `XP menu` -> `Content Studio`.

Content Studio has three parts: a project bar across the top, a menu bar on the left, and a main panel that fills the rest. The menu bar holds the content navigator, items contributed by installed apps, and *Settings* at the very bottom. For more than this chapter covers, see the https://developer.enonic.com/docs/content-studio[Content Studio documentation].

=== Task: your first project

When you open Content Studio for the first time, it offers to create a project:

.No projects found dialog
image::cs-project-create.png["Content Studio dialog offering to start the project wizard", 660px]

Content in Enonic is stored in _content projects_, or simply _projects_.
Each project has its own permissions, languages and other settings, and its own selection of apps.

Click btn:[Start Project wizard] and follow the steps to create your first project:

. Choose a default language, for instance `English`.
. Give the project the display name "{cms-project-displayname}". The identifier is derived from it, and becomes `{cms-project-id}`.
+
NOTE: The project identifier is important, and cannot be changed later. Later chapters refer to the project as `{cms-project-id}`, so stick with that name if you want to copy their examples verbatim.
+
. Choose the `Public` access mode. This lets anyone read published content, which is what we want for a public website for instance
. No need to change the roles. You are the super user, so you already have access.
. In the "Applications" step, select the `Developer 101` app you deployed earlier.

.Project summary showing the values you have set in the wizard
image::cs-project-summary.png["Content Studio project creation summary", 964w]

TIP: Only apps that contain a CMS descriptor, `cms/cms.yaml`, can be assigned to a project. The vanilla starter includes one out of the box.

== What are content types?

Every content item has a content type, which defines the data fields the item can and must have.
Content Studio validates the item against its content type as editors fill in the form.

Content types are defined in apps, while content projects hold the content.
Assigning an app to a project is what connects the two: editors can then create the app's content types in that project. This also means you may re-use the same apps and schemas across multiple projects.

=== Task: your first content type

You'll create a content type with two fields. In Content Studio, its form will look like this:

// TODO(xp8-verify): recapture from Content Studio 6.1
.The target for your first content type
image::content-type-target.png["A content creation form with legal name and biography fields"]

In your editor, open the app folder, `{app-name}/`, that you created in the previous chapter.
All paths are relative to it.

. Content types live in `{app-root}/cms/content-types/`, which the starter created.
XP expects each content type in a directory of its own, so create a directory called `artist` there.

. In the `artist` directory, create a file called `artist.yaml`.
The file name must match the directory name, so the full path is `{app-root}/cms/content-types/artist/artist.yaml`.

. Add the following content:
+
.The 'Artist' content type
[source,yaml]
----
include::../{app-root}/cms/content-types/artist/artist.yaml[tags=header;basics]
----
+
* `kind`: Every schema file starts by declaring what kind of schema it is.
* `title`: The name editors see when they create content.
* `description`: Optional, but it helps your editors.
* `displayNamePlaceholder`: The hint shown in the built-in display name field, here telling editors it holds the artist's stage name.
* `form`: The fields editors fill in.
* `type` and `label`: The kind of input editors see, and its label.
+
[TIP]
.When to use it
====
Every content type has a built-in display name, so don't add a `title` or `name` field that stores the same thing: editors get two fields to fill in, and your front-end gets two places to look. Here the display name is the artist's stage name and `legalName` is the name on their official documents, which is why both earn their place. Add a field only when it carries different information from the item's name.
====
+
NOTE: Content types have more optional settings, described in https://developer.enonic.com/docs/cms/stable/content/content-types[the reference documentation].
The fields are form items, not HTML `input` elements; <<form-items#, the form items chapter>> covers them.

=== Names and namespaces

XP identifies the content type you just created as `{app-name-full}:artist` - the app name, a colon, and the file name. The app name acts as a _namespace_: everything an app ships, from content types to mixins and APIs, is prefixed with it. This isolates the schemas and functionality of one app from every other app on the same instance, so two apps never conflict, even if both define a content type called `artist`.

The types XP ships with use reserved namespaces, such as `base:folder` and `media:image`. You will meet these qualified names again when querying the API.

NOTE: Read more about https://developer.enonic.com/docs/cms/stable/schemas/namespaces[namespaces] in the CMS reference docs.

=== Deploying the content type

If `enonic dev` is still running from the previous chapter, it redeploys your app as soon as you save the file.
If not, start it again from the app folder:

[source,shell]
----
enonic dev
----

TIP: XP validates every schema when the app is deployed. A typo in a key, such as `helptext` instead of `helpText`, is rejected and reported in the sandbox log, so keep an eye on it whenever you change a schema.

== Publishing your content

Content Studio shows a status on every item: _Work in progress_ for unpublished changes, _Ready for publishing_ once an editor has marked it, and _Published_ when nothing has changed since publishing.
Content that does not validate against its content type, for instance because a required field is empty, is marked as invalid.

// TODO(xp8-verify): check the status names and icons against Content Studio 6.1 and recapture the screenshot
image::content-studio-content-status.png[Three pieces of content displaying different statuses, 270w]

Every content project has two branches.
You create and edit content in the _draft_ branch, and publishing copies it to the _master_ branch, which holds the published content.
When you edit published content, only draft changes until you publish again.

To publish an item, right-click it and select *Publish*.
You don't need to publish anything yet; the front-end chapter does it when the content needs to be public.
