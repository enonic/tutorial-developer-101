== Content Studio

Content Studio should already have been installed, and can be launched from XP Admin: `XP menu` -> `Content Studio`.

TIP: If you wish to install or update an application, this can be done from `XP menu` -> `Applications`.

Content Studio has three parts: a project bar across the top, a menu bar on the left, and a main panel that fills the rest. The menu bar holds the content navigator, items contributed by installed apps, and *Settings* at the very bottom. We will visit all of them during this tutorial.

=== Assigning an app to a project

Content Studio is a powerful app with a lot of features, and one of its main goals is to provide an awesome user experience for creating and curating content.

Content is defined through content types (a concept we'll introduce in the next section), which are defined and installed via applications.

Therefore, if we want to enable Content Studio to manage a specific type of content, we need to access Content Studio in a project which has an app assigned to it, and in this app, this specific content should be defined via a content type.

With all this in mind, note that one of the steps in the wizard was to assign your app to the project. If you followed along, you should have your app assigned to your first project, and in case you missed it, no worries, let's assign it to the created project:

. Click *Settings* at the bottom of the menu bar on the left
. Double click on the project you just created to edit it
. Scroll down and in the "Applications" section, select the application you've previously deployed to this sandbox

== Apps vs content projects

We've reached a point in this guide where it's worth pausing to separate two things that both get called "project" elsewhere:

Your app:: The folder the Vanilla starter created for you, with its schemas and descriptor. When you run `enonic dev`, it is built and deployed to XP, where it runs as an application. Throughout this tutorial, "app" means both the folder you edit and the thing running in XP, because they are one and the same.
A content project:: A place in XP where content is stored, as explained above. Content can be created based on the apps you assign to the content project.

Apps define content types. Content projects hold content. Assigning an app to a content project is what connects the two. Now, back to work!

== What are content types?

Every content item created in Enonic has a specific content type. The content type defines the data fields (aka properties) that piece of content can and must have.

A JavaScript analogy: If a content type is a JSON schema, then the content item is a JSON that matches the schema. Actually, this is not so far from how things actually work - as you will see later!

IMPORTANT: As mentioned before, content types are defined and installed via applications. If you unassign an application from the project you're currently working on, you'll no longer be able to create or edit content of that type.

=== Task: your first content type

Now that we know what a content type is, let's look at how we create them.

We'll create a content type that contains two input fields. When shown in Content Studio, it will look like this:

// TODO(xp8-verify): recapture from Content Studio 6.1
.The target for your first content type
image::content-type-target.png["A content creation form with name and biography fields", {image-xl}]

Back to your preferred editor, make sure you're in the app folder (`{app-name}/`) that you created in a previous {document}. All paths will be relative to this root folder.

. Content types live in `{app-root}/cms/content-types/`. The starter created this directory for you. XP is quite particular about the app's folder structure, so you need to put content types right where it expects to find them.

. Create a directory called `{content-type-1}` in the `content-types/` directory. XP expects all content types to have their own directories.

. Within the `{content-type-1}` directory, create a file called `{content-type-1}.yaml`. The file name must match the directory name (except for the file extension). The full path to the content type from the app's root folder should be `{app-root}/cms/content-types/{content-type-1}/{content-type-1}.yaml`.

. In the `{content-type-1}.yaml` file, place the following content:
+
.The '{content-type-1-capitalized}' content type
[source,yaml,{subs}]
----
kind: "ContentType" # <1>
title: "{content-type-1-capitalized}" # <2>
description: "Information about an {content-type-1}" # <3>
superType: "base:structured"
form: # <4>
  - type: "TextLine" # <5>
    name: "name"
    label: "Name"
    helpText: "The {content-type-1}'s name (if different from their professional moniker)."
  - type: "TextArea"
    name: "about"
    label: "About the {content-type-1}"
----
+
<1> Every schema file starts by declaring what kind of schema it is.
<2> This is what will be displayed in Content Studio when creating new content.
<3> This is an optional description, but it is still recommended to add, as it will make life easier for your editors.
<4> This is where we specify which fields (aka inputs) this content type shall have, basically the form, as seen in Content Studio.
<5> The `type` specifies what kind of input the user will see in Content Studio, and the `label` specifies how the input will be labeled.
+
[TIP]
.When to use it
====
Every content type has a built-in display name, so don't add a `title` or `name` field that stores the same thing: editors get two fields to fill in, and your front-end gets two places to look. Here the display name is the artist's stage name and `name` is their legal name, which is why both earn their place. Add a field only when it carries different information from the item's name.
====
+
NOTE: Content types also have a number of other, optional settings that we won't get into here. If you'd like to learn more about this, consult https://developer.enonic.com/docs/cms/stable/content/content-types[the reference documentation].
+
NOTE: XP's inputs are _not_ the same as HTML `input` elements. To read more about them, <<form-items#, see the {document} on form items>>.

=== Names and namespaces

XP identifies the content type you just created as `{app-name-full}:{content-type-1}` - the app name, a colon, and the file name. The app name acts as a _namespace_: everything an app ships, from content types to mixins and APIs, is prefixed with it. This isolates the schemas and functionality of one app from every other app on the same instance, so two apps never conflict, even if both define a content type called `{content-type-1}`.

The types XP ships with use reserved namespaces, such as `base:folder` and `media:image`. You will meet these qualified names again when querying the API.

NOTE: Read more about https://developer.enonic.com/docs/cms/stable/schemas/namespaces[namespaces] in the CMS reference docs.

=== Deploying the content type

If `enonic dev` is still running from the previous {document}, it picks up the new file and redeploys your app. If not, start it again from the app folder:

[source,shell]
----
enonic dev
----

If everything goes well, you should see your sandbox logs update now. And that's the basics of creating new content types.

TIP: XP validates every schema when the app is deployed. A typo in a key, such as `helptext` instead of `helpText`, is rejected and reported in the sandbox log, so keep an eye on it whenever you change a schema.

== Publishing your content

You might have noticed the status indicators displayed on all the content we've been working on, both in the wizard and in the content grid. This is how Content Studio indicates whether something is published or not and whether there are any errors with it.

// TODO(xp8-verify): check the status names and icons against Content Studio 6.1 and recapture the screenshot
Error:: This indicates that there is something wrong with your content. Because XP uses structured content it can also validate content as it is created. If something doesn't conform to the specified schema (for example: a required field has no value), it will fail to validate and be marked as invalid.
Work in progress:: This piece of content has unpublished changes. That could be either because this is new content that has never been published, or it could be because there have been changes to this piece of content since it was last published.
Ready for publishing:: This piece of content is marked as ready to be published.
Published:: This piece of content is published and has not been modified since.

image::content-studio-content-status.png[Three pieces of content displaying different statuses, 270w]

So what does it mean for content to be published? It doesn't make much of a difference to us at this stage of the tutorial, but when you're working on production systems, it's very important. So let's talk briefly about Content Studio's branching and publishing system.

=== Branches

Every content project has two branches:

- _draft branch_, where you work and edit;
- _master branch_, holds the published content.

When you work on something in Content Studio, you're working on the *draft branch*.

When you publish something, the *master branch* gets updated with the new content.

When you edit that same piece of content in Content Studio again, you're back to working on the *draft*, and you have to publish it to see changes to the published content.

To publish a piece of content, right click it and select "Publish".
